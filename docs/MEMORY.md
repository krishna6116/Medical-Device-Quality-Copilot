## Why memory, and why it must be deletable

A field-failure investigation runs for weeks. Without memory, every session starts from zero and the same causes get re-checked. With memory, the assistant starts each session knowing what was ruled out (and why), the open hypotheses, decisions and questions. In a regulated company the user must also be able to see exactly what is remembered and delete it, with no hidden copies.

| Design rule | How |
|---|---|
| Where | PostgreSQL schema `memory` (created if missing, never dropped by the data loader): investigation (title, product code, manufacturer, status), memory_item (kind, text, evidence citations, status, session, source), session (start/end), memory_event (audit trail WITHOUT content: item id, kind, action, time) |
| Kinds | hypothesis, ruled_out, decision, open_question, note |
| Writing | only through explicit calls: the assistant's memory tools (remember, recall, update_memory, forget) or the user's API/CLI; every save returns a confirmation that is shown to the user |
| Reading | at the start of every session the investigation's current memory is rendered into a block added to the system prompt; recall returns the same content on demand |
| Guardrails | an item needs an open investigation; text 5-500 characters; evidence may only cite report keys and recall numbers that exist in core.fact_report / core.fact_recall; text with an email address or phone number is rejected; at most 200 items per investigation |
| Deletion | forget / delete_item removes the row; delete_investigation removes the investigation with its items and sessions; the audit trail keeps only ids, kinds, actions and times, never text; export writes everything that is stored, so the user can see there is nothing else |

| Scorecard item | Meaning | Result |
|---|---|---|
| S1_memory_store_correct | saving, reading, editing, deleting and exporting memory work exactly, and survive a data reload | pass |
| S2_remembers_across_sessions | each new session starts with exactly what the investigation has stored, nothing more or less | pass |
| S3_deletion_is_real | deleted memory is gone from every table; no hidden copy, the audit trail stores no text | pass |
| S4_guardrails_hold | invented evidence and personal data are refused; every save is confirmed to the user | pass |
| S5_export_and_ci | the export shows everything stored; tests run in CI on a real database | pass |

- **Across sessions:** 7/7 session memory blocks equal an independent replay of every save, edit and deletion; the final database equals the same model.
- **Deletion:** 4 deleted or refused texts (12 search patterns, including the first and last 30 characters of each) were searched in 12 text columns: 0 hits. Audit-trail columns: action, actor, kind (no text). The scanner's self-test catches a planted partial copy, so this check can fail.
- **Guardrails:** 10 bad saves refused in the API probe (invented report, invented recall, malformed evidence, email, phone, empty, too long, wrong kind, closed investigation, missing investigation); in the scenarios an invented report key, a phone number and a cross-investigation delete were refused, and every save was confirmed in the answer.

*Post hoc (found while building, before the phase was called done):* the first version of the deletion scan only searched for whole texts and missed a planted partial copy; it now also searches the start and end of each text and self-tests on every run.

## Using it

```powershell
.venv\Scripts\python -m mdqc.memory list
.venv\Scripts\python -m mdqc.memory show 1
.venv\Scripts\python -m mdqc.memory export 1 --md
.venv\Scripts\python -m mdqc.memory delete-item 12
.venv\Scripts\python -m mdqc.memory delete 1
```

Phase 8's app adds a memory page with the same view, edit, export and delete actions.

## Limits

- The scenarios use the scripted stand-in, so they prove the memory machinery, not that a model uses memory wisely (saving the right things, not re-checking what was ruled out). Phase 6 measures that with the real model.
- Single-user and local: there are no accounts. A shared deployment would need per-user access control.
- Model providers keep request logs under their own retention policies; deleting memory here does not reach copies of past prompts held elsewhere. The app's cloud demo replays recordings and sends nothing.

## Why we did these tasks

| Task | Why we did it | What we learned | What it changes next |
|---|---|---|---|
| Separate memory schema | Memory must survive data reloads and stay apart from FDA data | A data reload into another schema leaves memory untouched (tested) | Phase 8's memory page reads this schema |
| Explicit memory tools with confirmations | The user must always know what was saved | Every scripted save is echoed in the answer; the assistant cannot touch another investigation | Phase 6 checks the real model confirms its saves |
| Guardrails on evidence and personal data | Memory must not hold invented evidence or personal data | Invented report keys, phone numbers and emails are refused before anything is stored | Phase 7 adds wider guardrail tests |
| Real deletion with a text-free audit trail | Deleting must leave no copy behind | A deletion scan that searched whole texts missed a partial copy; it now self-tests | Same pattern for any future store |
| Independent replay of every memory action | To prove each session saw exactly the right memory | 7/7 sessions matched | Phase 6 adds multi-session questions for the real model |

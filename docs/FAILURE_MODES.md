## What a failure mode is, and why group reports

A failure mode is *how* a device failed (an implant came loose, a pod's cannula bent, a pacemaker battery ran down early). Quality engineers track complaints by failure mode because each mode has different causes and fixes. Phase 1 expected FDA's own problem terms to be too coarse (the top term for most codes says no device problem was identified), so the mode would have to be read from the narrative. Phase 3 tested that expectation and it did not hold: device *and patient* problem terms together, mapped through the codebook, were the best method.

**What this means** (descriptive; per-family test sets are only 20-60 reports, so these are hints, not claims):

- FDA's coded terms are a strong baseline: manufacturers already code their reports, and the codebook maps those codes well (test 70%).
- orthopedic: best on test was M1 (65%; FDA terms 65%).
- cardiac: best on test was M2 (80%; FDA terms 65%).
- diabetes: best on test was M1 (90%; FDA terms 90%).
- Comparing a report with one-sentence mode definitions (M3) does not work here (test 32%); its thresholds made no difference on validation. Narratives are long and full of regulatory boilerplate, which a short definition does not resemble.
- A family-specific combination (e.g. keywords for pacemakers) looks promising but was not pre-registered; trying it now would be tuning on the test set, so it is left as an idea for a future, separately registered test.

## Similar-report search

Given one report, find others with the same failure mode. Evaluated on the labelled reports: each non-'other' report is a query; the other labelled reports of the same code and split are the candidates; a candidate is relevant if it has the same reference mode. MRR = average of 1/(rank of the first relevant result).

## Early-warning signals and the recall backtest

Rule (pre-registered): month t (2023-01 or later, so 12 months of history exist) is a SIGNAL if count_t >= 5 and the Poisson probability of seeing count_t or more, with mean = average of the previous 12 months (at least 0.5), is below 0.001.

- **214 signals** in 2023-2024 (107.0 per year) across 91 of 475 (code, company, mode) series. By code: JWH 96, LPH 41, LWP 34, LZG 30, MBH 13.
- **Backtest:** 15 of 38 recall events initiated in 2023-2024 had a signal for the same code and company in the 6 months before (hit rate 39%). For comparison, 14% of all 7-month windows contain a signal (base rate).
- **Reading it honestly:** hits are more frequent than the base rate, but there are few recall events, they cluster in a few companies, and a signal is a prompt to look, not evidence of a defect. Many recalls concern labeling, packaging or instruments that patients' reports would not show.

## Differences from the project plan (and why)

`docs/PLAN.md` was written before Phase 3's criteria. Where they differ, the committed criteria (`config/phase3_criteria.json`) were followed:

- **Sample split by report, not by product code.** The project convention is to split by product code, but every method here is rule-based or zero-shot and nothing is trained on the labels; the labels only choose among a few pre-registered settings. Splitting by code would have put whole device families only in validation or only in test, so the 20/20 split is made inside each code instead (`mdqc/phase3_sample.py`).
- **No embedding *clustering* method.** The plan listed it; the registered methods (M1-M5) used embeddings for matching reports to mode definitions (M3) and clustering only with TF-IDF (M5).
- **MRR and precision@5 instead of recall@k** for similar-report search, as registered.
- **No multiple-comparison correction needed:** one pre-registered comparison per question (chosen method vs FDA terms; chosen search vs BM25), so Holm's correction does not change anything.
- **No Claude labelling in Phase 3:** the user chose to keep this phase free; the project's only paid run is Phase 6.

## Why we did these tasks

| Task | Why we did it | What we learned | What it changes next |
|---|---|---|---|
| Codebook before labels, labels before methods | So neither the labels nor the methods could drift toward the other | Writing definitions first forces hard choices (cause vs symptom, priority order) | Phase 6 reuses the same labels to grade the assistant |
| Five methods, chosen on validation, tested once | To learn whether anything beats FDA's own coded terms, without fooling ourselves | M1 won on validation; test accuracy 70% vs 70% for FDA terms | Phase 4's failure-mode tool uses the chosen method |
| Local embedding model | Meaning-based grouping and search for free on a laptop | 154k reports embedded on CPU; search: R2_embedding chosen | Phase 4 similar-report search runs locally at no cost |
| Alert rule per company and mode, backtested | A quality engineer wants early warning, not hindsight | 15/38 recall events had a prior signal; base rate 14% | Phase 7 monitoring reuses the rule on new reports; the assistant presents signals as prompts, not proof |
| Independent verifier and scorecard | Every number recomputed by separate code | Scorecard 5/5 | Same pattern for the assistant's evaluation in Phase 6 |
